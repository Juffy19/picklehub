## 1. Purpose and Working Rules

- `Notes.md` is the shared decision and checkpoint tracker for the project
  owner and ChatGPT.
- Formal requirements and database decisions remain in their designated
  project documents (section 2). If this file and a formal document differ,
  the formal document governs until the difference is reconciled.
- Only decisions explicitly approved by the project owner count as
  approved. A proposal, recommendation, or open question is not a decision.
- Approving an individual decision does not finalize a step.
- Do not invent or silently change decisions.
- Claude Code is responsible for manipulating project files and GitHub.
- For every step, the step's own document and this file are the primary
  files to update (workflow rule: `CLAUDE.md` section 13, "Step
  Documentation Workflow").

## 3. Step 6.1 — Database Conventions

Status: **Approved — Verified** (`docs/04` section 2; rules summarized in
`CLAUDE.md` section 15).

| ID | Area | Summary |
| --- | --- | --- |
| C1 | Primary keys | UUID keys generated by PostgreSQL/Supabase; identity originates in Supabase Auth |
| C2 | Foreign keys | Singular entity name + `_id`; descriptive actor references; matching types |
| C3 | Timestamps | `TIMESTAMPTZ` for instants; `created_at` defaults to `NOW()`; `updated_at` on mutable records; UTC interchange |
| C4 | Timezones | IANA facility timezone; local-time schedules; historical occurrences never silently rewritten |
| C5 | Lifecycle statuses | `TEXT` + `CHECK`; changing permitted values needs a reviewed migration; ordinary transitions do not |
| C6 | Controlled fixed values | `TEXT` + `CHECK`; no PostgreSQL ENUM types without a reviewed decision |
| C7 | Deletion | Purpose-based, not universal soft deletion; history preserved |
| C8 | Audit fields | `created_by_user_id` / `updated_by_user_id` where meaningful; not authorization, not audit history |
| C9 | Naming | `snake_case`, plural tables, `id` keys; prefixes `pk_`, `fk_`, `uq_`, `ck_`, `ex_`, `idx_` |
| C10 | Schema and security | `public` schema for MVP; access via grants, RLS, and server-side authorization |

These are concise summaries; the reviewed wording in `docs/04` section 2
governs (item 10).

## 5. Key Step 5 Dependencies

Step 5 (`docs/03-step-5-database-decisions.md`) remains the authority for
business rules and lifecycles. Rules Step 6.2 depends on:

- Supabase Auth is the authentication authority; Auth User → Profile 1:1;
  stable identity `user_id`; display name is not an identity key (§5.33,
  §4.3).
- Global roles `PLAYER` and `FACILITY_ADMIN`; one account may hold both;
  Session Host, Open Play Host, Authorized Scorer are contextual (U14, U19,
  I5/I6).
- Profile status `ACTIVE` / `DEACTIVATED`; deactivation preserves history;
  no self-assigned `FACILITY_ADMIN` (§5.33).
- Guest Identity separate and private-context scoped (§5.10, I14).
- Notifications: in-app and email; email failure never rolls back a core
  transaction; notifications retained; no automatic expiration; preferences
  deferred (§5.30).
- Audit History append-oriented and retained; users cannot edit or delete
  (§5.32, §7).
- Session Host may confirm a Game they played in (U17); dispute resolution
  excludes conflicted admins (I1).
- Official statistics use only authoritative, eligible, confirmed results
  (U1, U3, U4, U16).
