## 2. Step 6.1 — Database Conventions

Decision status: **APPROVED**

These conventions apply to all physical schema work. Items described as
"remain to be designed" are intentionally open and must not be decided by
assumption during implementation.

### C1 — Primary Keys

- Use UUID primary keys for physical database entities.
- UUIDs are generated by PostgreSQL/Supabase.
- Authenticated user identity originates in Supabase Auth and is related to
  the application profile.
- Exact physical identity relationships are finalized during the
  identity-design section (Step 6.2).

Preserves Step 5: Supabase Auth is the authentication authority; Auth User
→ Profile is 1:1; the stable identity is `user_id`; Guest Identity remains
separate from Profile (5.33, 4.3, I14).

Step 6.2 update: 6.2.1 decides that the Profile primary key and Auth foreign
key use the Supabase Auth user UUID (section 3.1).

### C2 — Foreign Keys

- Use singular entity names followed by `_id`, such as `booking_id`,
  `court_id`, and `user_id`.
- Use descriptive actor references such as `created_by_user_id` where
  applicable.
- Foreign key column types must match their referenced columns.

### C3 — Timestamps

- Use PostgreSQL `TIMESTAMPTZ` for actual instants.
- `created_at` defaults to `NOW()`.
- Applicable mutable records use `updated_at`.
- The application uses UTC for timestamp interchange and the facility
  timezone for schedule display.
- Do not confuse actual instants with local recurring schedules.

### C4 — Timezones

- Each facility has an IANA timezone identifier.
- Operating hours and recurring Open Play schedules use local facility
  time.
- Individual scheduled occurrences resolve to actual instants represented
  by `TIMESTAMPTZ`.
- Historical occurrence timestamps must not be silently rewritten when
  facility timezone configuration changes.
- Exact physical representations and timezone-change procedures remain
  part of physical schema design.

Preserves Step 5: the facility timezone is facility data (5.11) and is not
duplicated in Facility Configuration (5.34); operating hours use local
facility time and timestamps are persisted in UTC (5.12); Recurring Open
Play Schedules are defined in facility time and generate independent
instances that schedule changes never rewrite (U8, B2).

### C5 — Lifecycle Statuses

- Use `TEXT` with database-level `CHECK` constraints.
- Each entity's status column enforces its exact approved lifecycle values.
- Application types and validation must remain consistent with database
  constraints.
- Changing the permitted status values enforced by a database `CHECK`
  constraint requires a reviewed database migration.
- Ordinary record-level lifecycle transitions (a record moving from one
  permitted status to another) do not require a migration.
- Normal lifecycle transitions must use authorized business operations and
  respect the approved Step 5 lifecycle rules.

The approved lifecycle values are those in
`docs/03-step-5-database-decisions.md` (sections 3 and 10, with the
section 11 supersessions). This convention does not add, remove, or rename
any lifecycle value.

### C6 — Controlled Fixed-Value Fields

- Use `TEXT` with database `CHECK` constraints for all controlled
  fixed-value fields in the MVP, including statuses, session modes, skill
  levels, and categories.
- Do not use PostgreSQL ENUM types unless a future reviewed decision
  establishes a specific need.
- Do not apply constraints to genuinely free-form text without a
  documented reason.

### C7 — Deletion

- Use purpose-based deletion, not universal soft deletion.
- Preserve historical records according to approved rules.
- Use lifecycle states for cancellation/completion and inactive states
  where appropriate.
- Hard deletion is allowed only when retention, privacy, and
  referential-integrity requirements permit it.
- Add soft-deletion fields only for documented entity-specific
  requirements.
- Exact retention and foreign-key deletion behavior remain to be designed.

Preserves Step 5: the historical data rules (section 7); versioned Game
Results that are never overwritten (U1, B1); retained dispute history;
append-oriented audit history that users cannot edit or delete (5.32);
profile deactivation that preserves history (5.33); and cancellation that
retains the cancelled record, for example Facility Closures (5.12).

### C8 — Audit Fields

- Use `created_at` and `updated_at` according to the timestamp conventions.
- Add `created_by_user_id` and `updated_by_user_id` where actor attribution
  is meaningful.
- System-generated operations may lack a direct human actor.
- Actor metadata does not establish authorization and does not replace
  dedicated audit history.
- Exact field coverage and nullability remain to be designed.

Preserves Step 5: Audit History is a separate, locked entity (5.32); audit
fields on a record are not a substitute for it.

### C9 — Naming

- Use lowercase `snake_case` identifiers.
- Use plural table names.
- Use descriptive column names.
- Name primary key columns `id`.
- Follow the approved singular-entity-plus-`_id` foreign key convention
  (C2).
- Use descriptive constraint and index names with these prefixes:

  | Prefix | Used for |
  | --- | --- |
  | `pk_` | Primary key constraints |
  | `fk_` | Foreign key constraints |
  | `uq_` | Unique constraints |
  | `ck_` | Check constraints |
  | `ex_` | Exclusion constraints |
  | `idx_` | Indexes |

- A descriptive name follows the prefix. The exact pattern of the
  descriptive part is not fixed by C9.
- Use descriptive, action-oriented `snake_case` database function names.
- Avoid quoted case-sensitive identifiers and unnecessary abbreviations.

Illustrative only: a check constraint on the status column of a
hypothetical `examples` table could be named `ck_examples_status`. Naming
examples do not approve any table, field, unique constraint, exclusion
constraint, or index for the physical schema; those are decided in the
relevant schema-design sections.

### C10 — Schema Organization and Security

- Use PostgreSQL's `public` schema for MVP application tables.
- Do not interpret `public` as unrestricted public access.
- Control access through explicit grants, RLS, and server-side
  authorization.
- Design privileged database operations with explicit execution
  permissions and security boundaries.
- Introduce additional schemas only when a documented security or
  architectural requirement justifies them.
- Exact RLS policies, grants, and database-function security settings
  remain future design work.

Preserves the architecture: RLS is a second protection layer, sensitive
writes are server-authoritative, and privileged credentials stay
server-only (`docs/02-application-architecture.md` sections 5, 6.4, 7).

### 3.1 Identity, Global Roles, and Profile (6.2.1–6.2.24)

- **6.2.1** — The Profile primary key and Auth foreign key use the Supabase
  Auth user UUID.
- **6.2.2** — Global roles are separate assignments: PLAYER and
  FACILITY_ADMIN.
- **6.2.3** — Contextual permissions are derived from relationships, including
  Session Host, Open Play Host, and Authorized Scorer.
- **6.2.4** — Provision Profiles automatically through a trusted database-side
  mechanism or equivalent.
- **6.2.5** — Deactivate and preserve records; handle permanent deletion
  through a separately reviewed policy.
- **6.2.6** — Preserve global-role grant/revoke history; only active
  assignments grant access.
- **6.2.7** — Global-role grants require trusted server-side authority; users
  cannot promote themselves.
- **6.2.8** — Global roles apply account-wide; facility-specific authority
  remains contextual.
- **6.2.9** — Deactivation revokes active global roles while preserving
  history. Reactivation does not restore them.
- **6.2.10** — Supabase Auth owns credentials, identity, and email; Profile
  owns application profile data.
- **6.2.11** — Account creation should fail or roll back if Profile creation
  fails. Actual Supabase transaction behavior must be verified during
  implementation.
- **6.2.12** — Reactivation does not restore revoked roles.
- **6.2.13** — Store display name in Profile, not Auth metadata. Display name
  is not an identity key.
- **6.2.14** — Auth is authoritative for email; do not duplicate authoritative
  email in Profile.
- **6.2.15** — Public Profiles expose only explicitly approved public fields.
- **6.2.16** — Approved aggregate statistics may be public and must use only
  authoritative, eligible results.
- **6.2.17** — Users may edit their own approved Profile fields; protected
  fields require trusted authorization.
- **6.2.18** — Use timestamps and targeted audit history for privileged
  actions.
- **6.2.19** — Self-reported skill level is optional.
- **6.2.20** — Approved skill-level values are BEGINNER, INTERMEDIATE, and
  ADVANCED.
- **6.2.21** — Skill level is nullable.
- **6.2.22** — Skill level is public when set and can be updated or cleared by
  the user.
- **6.2.23** — User IANA timezone is optional; facility timezone remains
  authoritative for facility schedules.
- **6.2.24** — The MVP uses one app-wide language; Profile does not need a
  locale field.

### 3.2 Avatar Upload and Processing (6.2.25–6.2.43)

- **6.2.25** — Avatar upload is optional.
- **6.2.26** — Use a public avatar bucket for images intentionally made
  public.
- **6.2.27** — Accept JPEG, PNG, and WebP.
- **6.2.28** — Maximum upload size is 5 MB.
- **6.2.29** — Maximum dimensions are 1024 × 1024 pixels.
- **6.2.30** — Generate a square derivative.
- **6.2.31** — Process the replacement before changing the Profile reference;
  make cleanup safely retryable.
- **6.2.32** — Removing an avatar clears its Profile reference and initiates
  source/derivative cleanup. Cached public copies may persist temporarily.
- **6.2.33** — Use server-controlled, user-specific storage paths. Public read
  access does not grant public write/delete access.
- **6.2.34** — Generate filenames on the server.
- **6.2.35** — Strip EXIF metadata, including GPS and device information.
- **6.2.36** — If processing fails, preserve the old avatar, clean up
  incomplete files, and return a recoverable error.
- **6.2.37** — Server-side image processing is authoritative.
- **6.2.38** — Enforce upload and processing rate limits server-side.
- **6.2.39** — Require authenticated authorization to edit Profile; no special
  email-verification requirement was approved for avatar editing.
- **6.2.40** — Deactivation removes the avatar from public delivery and
  schedules cleanup.
- **6.2.41** — Reactivation requires a new avatar upload; the old avatar is
  not automatically republished.
- **6.2.42** — Deactivated Profiles and public statistics are hidden while
  historical records are preserved.
- **6.2.43** — After authorized reactivation, public Profile/stat visibility
  returns automatically; the avatar remains the default until a new upload.

### 3.3 Username Rules and Security (6.2.44–6.2.58)

- **6.2.44** — Use username-based public Profile URLs.
- **6.2.45** — Reserve previous usernames and redirect them to the current
  Profile URL.
- **6.2.46** — Allow lowercase letters, numbers, hyphens, and underscores.
  Enforce case-insensitive uniqueness and prohibit leading, trailing, or
  consecutive separators.
- **6.2.47** — Username length is 3–30 characters.
- **6.2.48** — Reserve system and administrative usernames, including examples
  such as admin, support, api, login, signup, and settings.
- **6.2.49** — Limit normal username changes to once every 30 days, with an
  administrative recovery process.
- **6.2.50** — Require recent authentication before a normal username change.
- **6.2.51** — After a successful change, send an in-app confirmation and an
  email to the verified Auth email with security guidance. Notification
  failure does not undo the change.
- **6.2.52** — Retain username history and security audit metadata, including
  old/new usernames, timestamp, account reference, method, and authorization
  outcome, while minimizing sensitive data.
- **6.2.53** — Users may see their own username history. Authorized
  administrators may access it for legitimate purposes. The public cannot see
  other users' histories; security metadata is restricted.
- **6.2.54** — Separate long-lived username reservations and redirects from
  detailed audit metadata, with defined retention policies.
- **6.2.55** — Permanent deletion requires a separate policy considering
  privacy, impersonation, redirects, historical records, and data
  minimization. Usernames are not automatically released.
- **6.2.56** — Deactivated users cannot make normal username changes.
  Authorized support/admin exceptions are possible with applicable rules,
  history, and notifications; the Profile remains hidden.
- **6.2.57** — Administrators may bypass the 30-day cooldown with
  justification and audit logging.
- **6.2.58** — Normal cooldown exceptions require independent
  second-administrator approval. A restricted emergency path is allowed with
  documentation and retrospective review.

### 3.4 Username-Change Emergency and Administrative Review (6.2.59–6.2.91)

- **6.2.59** — Require retrospective review of emergency username changes
  within 72 hours.
- **6.2.60** — If the review deadline is missed, automatically escalate to a
  senior administrator/security owner. Track overdue status, document
  resolution, and do not automatically reverse the username change.
- **6.2.61** — Administrative username changes trigger enhanced in-app and
  email notification explaining the action and providing security/support
  guidance.
- **6.2.62** — Use risk-based approval: routine corrections require one
  administrator, a reason, and an audit record; sensitive cases such as
  disputed ownership, impersonation, or security incidents require a second
  administrator.
- **6.2.63** — Provide a formal player appeal and an independent reviewer
  where practicable, with a documented outcome.
- **6.2.64** — Players have 30 calendar days from notification to appeal, with
  exceptions for legitimate inability to appeal.
- **6.2.65** — Aim to decide the initial appeal within seven calendar days and
  update the player if more investigation is required.
- **6.2.66** — The reviewer selects an appropriate remedy with rationale and
  safeguards—for example, restoring the previous username if safe, choosing
  another valid username, or applying another justified correction.
- **6.2.67** — If an independent reviewer is unavailable, escalate to an
  uninvolved senior administrator. If none is available, leave the case
  pending and document the delay.
- **6.2.68** — Escalate to a senior administrator if no independent reviewer
  has been assigned within 24 hours.
- **6.2.69** — Allow one further review by a more senior authority after the
  first appeal. The player explains the reason; the second-level review
  normally concludes the appeal process. Separate corrections for significant
  errors or security issues remain possible.
- **6.2.70** — A player has 14 calendar days from notification of the first
  appeal outcome to request second-level review.
- **6.2.71** — Aim to decide second-level review within 14 calendar days and
  update the player if delayed.
- **6.2.72** — If the second-level deadline is missed, escalate to the
  designated senior authority, track overdue status, and update the player. No
  automatic outcome.
- **6.2.73** — The facility owner or formally designated delegate makes the
  final decision after second-level review, subject to conflict safeguards.
- **6.2.74** — Reopen a final decision for material new evidence or
  significant procedural error, subject to authorization and audit.
- **6.2.75** — A player or authorized administrator may request reopening.
- **6.2.76** — No fixed deadline applies to a qualifying reopening request,
  subject to authorization and retention constraints.
- **6.2.77** — An independent authorized reviewer who was uninvolved earlier
  decides whether a case qualifies for reopening.
- **6.2.78** — The same independent reviewer who approves reopening conducts
  the substantive review.
- **6.2.79** — Aim to decide the reopened case within 14 calendar days after
  reopening approval.
- **6.2.80** — If that deadline is missed, notify the player, explain the
  delay where appropriate, and continue the review. Do not impose an automatic
  result.
- **6.2.81** — After the reopened review, the facility owner/delegate makes
  the final decision, considering the independent reviewer's findings.
- **6.2.82** — Provide detailed in-app and email decision notices with the
  outcome, main reasons, username action, and support guidance. Do not
  disclose sensitive security information; preserve privacy.
- **6.2.83** — Allow one reopening per case. After the reopened case reaches a
  final decision, no further normal reopening is allowed; separately
  authorized corrections for serious issues remain possible.
- **6.2.84** — Allow restricted administrative correction after the reopening
  limit for serious security issues or significant errors, with authorized
  approval, reason, and full audit.
- **6.2.85** — Any authorized senior administrator may approve an exceptional
  correction, with reason and audit logging.
- **6.2.86** — Exceptional corrections require audit logging but no mandatory
  separate post-correction review unless a concern or applicable policy
  requires it.
- **6.2.87** — Notify the player about exceptional corrections unless a
  documented security/legal reason requires withholding notice. Default to
  in-app and email, respecting deactivated-Profile privacy.
- **6.2.88** — Email failures receive retries and recorded attempts.
  Persistent failures escalate. The correction remains successful; use in-app
  notification where applicable.
- **6.2.89** — Allow five total email attempts, including the initial attempt,
  before escalation.
- **6.2.90** — Use increasing retry intervals: 5 minutes, 15 minutes, 1 hour,
  and 6 hours after successive failures. Validate these timings during
  implementation.
- **6.2.91** — Permanent email-delivery failure ends email retries. Use
  another approved channel if available, record the failure, and escalate if
  notification remains unsuccessful. The correction remains successful.

### 3.5 Notification Queue and Escalation Reliability (6.2.92–6.2.99)

- **6.2.92** — Keep notification delivery outcome separate from
  escalation/resolution status.
- **6.2.93** — Use a database-backed retry queue, trusted background worker,
  and durable job/state tracking.
- **6.2.94** — Claim jobs atomically using a time-limited lease so another
  worker can recover the job after lease expiration.
- **6.2.95** — Recover expired leases with safeguards, recovery records, retry
  limits, and backoff. Duplicate delivery may still occur.
- **6.2.96** — Use a small set of priorities: security-critical, important
  account notifications, and routine notifications. Prevent starvation of
  lower-priority jobs.
- **6.2.97** — Define expiration windows by notification type. Mark expired
  jobs rather than sending stale notifications, and escalate applicable
  failures.
- **6.2.98** — If a high-priority security notification expires, escalate to
  the designated administrator/security owner, stop automatic delivery of that
  expired message, and do not automatically create a replacement.
- **6.2.99** — Failed escalation notifications receive bounded retries and
  tracking. If delivery still fails, the escalation remains unresolved.

### 3.6 Notification Job State and Delivery (6.2.100–6.2.114)

- **6.2.100** — Option C — Separate job state from attempt history. Store the
  job's compact current state separately from each delivery-attempt event.
- **6.2.101** — Option C — Structured outcome and error details. Record a
  controlled outcome category, an error code when available, and diagnostic
  details while minimizing sensitive data.
- **6.2.102** — Option C — Full deduplication and reconciliation. Use
  idempotency keys, provider message identifiers where available, attempt
  history, and reconciliation for uncertain delivery outcomes. Exactly-once
  delivery cannot be guaranteed.
- **6.2.103** — Option C — Explicit terminal outcomes. Distinguish successful
  delivery, permanent failure, and expiration; keep retryable jobs eligible
  for further processing.
- **6.2.104** — Option C — Controlled cancellation throughout processing.
  Allow cancellation of pending or retry-waiting jobs and request cancellation
  during processing where feasible. An email already accepted or delivered
  cannot be recalled.
- **6.2.105** — Option C — Risk-based cancellation controls. Routine
  notifications use normal rules; security-critical notifications require
  elevated authorization, justification, and audit. Emergency cancellation
  uses a restricted path and retrospective review.
- **6.2.106** — Option C — Atomic authorization plus delivery reconciliation.
  Coordinate cancellation and dispatch authorization, record the dispatch
  boundary, and reconcile uncertain outcomes.
- **6.2.107** — Option C — Classification-based retention. Determine audit
  retention based on priority, cancellation type, security relevance, privacy
  requirements, and data minimization.
- **6.2.108** — Option C — Contextual, least-privilege authorization. Base
  cancellation permissions on actor role, notification type, priority, and job
  state, enforced by trusted server-side logic.
- **6.2.109** — Option C — Idempotent cancellation with request auditing.
  Repeated requests must not create duplicate cancellation effects; record
  repeated requests when operationally relevant.
- **6.2.110** — Option C — Expired-job handling. Preserve EXPIRED, return the
  current status, and record the cancellation attempt when relevant. Do not
  reclassify expiration as cancellation.
- **6.2.111** — Option C — Successfully delivered job handling. Preserve
  successful delivery, return the current status, and audit the attempted
  cancellation when relevant. Do not claim the notification was cancelled.
- **6.2.112** — Option C — Permanently failed job handling. Preserve permanent
  failure and the original failure history; do not reclassify it as
  cancellation.
- **6.2.113** — Option C — Contextual escalation handling. Cancelling a
  notification does not automatically resolve an associated escalation. An
  authorized actor must resolve or dismiss the escalation separately.
- **6.2.114** — Option C — Auditable escalation resolution. Record the
  resolution outcome, timestamp, resolving actor, required reason, relevant
  notification/cancellation references, and applicable priority-based
  safeguards.

### 3.7 Escalation Reopening and Mandatory Review (6.2.115–6.2.127)

- **6.2.115** — Option C — Controlled reopening with contextual safeguards.
  Allow reopening for material new evidence, significant error, or unresolved
  underlying issues. Preserve the previous resolution and complete history.
- **6.2.116** — Option C — Controlled repeat reopening. Allow repeated
  reopening when justified, with documented reasons and stronger review for
  concerning patterns.
- **6.2.117** — Option C — Risk-based thresholds with mandatory review
  triggers. Define risk-based thresholds and trigger review for conditions
  such as repeated reopening without new evidence, conflicting decisions, or
  suspected misuse.
- **6.2.118** — Option C — Risk-based review controls. Routine cases continue
  normally. Security-critical or potentially misused cases may restrict
  further state changes while mandatory review is pending.
- **6.2.119** — Option C — Risk-based deadline and escalation. Set deadlines
  according to priority and risk. Missed deadlines trigger escalation, overdue
  tracking, and appropriate notifications without automatically deciding the
  case.
- **6.2.120** — Option C — Auditable decision with risk-based safeguards.
  Record decision, rationale, reviewer, timestamp, relevant evidence, and
  whether restrictions remain, change, or are lifted.
- **6.2.121** — Option C — Risk-based conflict management. Require recusal for
  material conflicts, independent reassignment where practicable, and
  documented handling when no independent reviewer is available.
- **6.2.122** — Option C — Risk-based reassignment deadline. Set reassignment
  deadlines by risk. Escalate missed deadlines to an uninvolved senior
  authority, record delays, and notify relevant parties where appropriate.
- **6.2.123** — Option C — Escalated independence safeguard. If no eligible
  senior reviewer is available, keep the review pending and escalate to a
  designated owner or independent authority without waiving independence
  requirements.
- **6.2.124** — Option C — Formal governance fallback. Document unavailable
  authorities and reassignment attempts. Consider an external independent
  authority only when policy permits and the authority is properly authorized.
- **6.2.125** — Option C — Risk-based fallback deadline and escalation.
  Escalate overdue fallback cases through the highest applicable governance
  channel while preserving pending status and independence requirements.
- **6.2.126** — Option C — Formal resumption with risk-based reassessment.
  When an eligible authority becomes available, verify independence and
  authorization, review accumulated history and material changes, reassess
  risk/deadlines, and formally resume the review.
- **6.2.127** — Option C — Risk-based evidence intake and governance
  escalation. Preserve new evidence, assess materiality through an authorized
  process, and escalate promptly if risk or urgency increases. Maintain the
  complete history and independence requirements.

### 3.8 Emergency Intervention and Protective Measures (6.2.128–6.2.131)

- **6.2.128** — Option C — Risk-based emergency intervention with safeguards.
  A designated, authorized emergency authority may take proportionate
  temporary protective action when credible evidence indicates immediate
  security or safety risk. Document the justification, audit the action,
  escalate promptly, and arrange independent retrospective review. The action
  must not prejudge the underlying case.
- **6.2.129** — Option C — Risk-based deadline and escalation. Set
  retrospective-review deadlines according to risk. Missed deadlines trigger
  escalation, overdue tracking, and appropriate notifications. They do not
  automatically validate or reverse emergency action.
- **6.2.130** — Option C — Risk-based reassessment and authorized termination.
  Periodically reassess temporary measures. An authorized decision-maker may
  lift, modify, or renew them based on current evidence, proportionality, and
  the ongoing threat. Record the decision and preserve independent-review
  requirements.
- **6.2.131** — Option C — Defined, risk-based resolution process. If the
  emergency authority and independent reviewer disagree, record both positions
  and supporting rationale. Refer the disagreement to an authorized,
  uninvolved senior decision-maker. Apply appropriate interim safeguards and
  document the final decision without prejudging the underlying case.

#### Item 2 — Public Profile Visibility

Issue: 6.2.15, 6.2.16, and 6.2.22 partially address Step 5 non-blocking

controls should determine visible information. Whether players can hide

Resolution — **RESOLVED** (2026-10-23). Clarifies 6.2.22 (and the related
6.2.15 and 6.2.16); their entries in section 3.1 are unchanged.

- Players can independently choose whether their profile information is
  publicly visible.
- Players can independently choose whether their approved aggregate game
  statistics are publicly visible. Displayed statistics must use
  authoritative, eligible results.
- Players can independently choose whether their self-reported skill level
  is publicly visible. Skill level remains optional, editable, and
  clearable.
- A private profile hides public profile information. Participation in
  bookings, Open Plays, and gameplay, and access to operational records,
  remain governed by the applicable rules for those activities.
- This is product behavior only.

Still open: physical database columns, tables, RLS policies, authorization
mechanisms, and implementation details.

Not addressed by this resolution: the default visibility setting for new
players (architecture Q28), and how player visibility choices interact with

#### Item 3 — Notification Expiration

Issue: 6.2.97 defines expiration windows for notification jobs, while

Resolution — **RESOLVED** (2026-10-23):

- A notification delivery job may expire when it is no longer useful to
  send, according to applicable expiration rules.
- Expiration of a delivery job does not automatically delete or expire the
  corresponding notification record.
- Notification records and their history follow separate retention rules.
  This decision does not establish automatic expiration or deletion of
  notification history.

Still open: exact expiration windows, retention periods, database
structures, and cleanup mechanisms.

#### Item 4 — Audit Retention

Issue: 6.2.54 and 6.2.107 call for defined or classification-based
retention, while Step 5 §5.32 and §7 retain historical audit records.

Resolution — **RESOLVED** (2026-10-23):

- Audit history must be preserved according to an approved retention
  policy.
- Retention periods may differ by audit-record classification.
- Records must not be deleted merely because they are old. Any eventual
  deletion must be governed by an explicitly approved retention policy.

Still open: exact retention periods, classifications, and deletion
procedures.

#### Item 5 — Username Cooldown Exceptions

Issue: 6.2.57, 6.2.58, and 6.2.62 differed on how many administrators a
cooldown exception or routine correction requires.

Resolution — **RESOLVED** (2026-10-23):

- Routine corrections without a cooldown bypass may be approved by one
  authorized administrator.
- Any correction bypassing the cooldown requires two authorized
  administrators, with the second approval independent of the first.
- Sensitive cases require two administrators even if the cooldown is not
  bypassed.
- Every cooldown bypass requires documented justification and an audit
  record.

Still open: the detailed criteria for classifying a case as sensitive.

#### Item 6 — Background Worker Architecture

Issue: 6.2.93 requires a trusted background worker; the architecture
(`docs/02-application-architecture.md` section 3) had no background
worker component.

Resolution — **RESOLVED** (2026-10-23):

- A background-processing capability is required for the approved
  notification and escalation workflows.
- It must support reliable processing and recovery from failures and
  respect approved job expiration, cancellation, and delivery-state rules.

Still open: the specific worker technology, hosting platform, scheduling
mechanism, detailed retry strategy, and deployment configuration.

#### Item 7 — User Timezone Versus Facility Timezone

Issue: 6.2.23 adds an optional user IANA timezone; the architecture
(section 5, item 11) presented dates and times in the facility timezone on
both server and client.

Resolution — **RESOLVED** (2026-10-23):

- The facility timezone is authoritative for facility operating hours,
  court availability, closures, and facility-based schedules.
- The user timezone is a display preference for presenting dates and
  times to individual users when appropriate.
- Actual events remain stored as timezone-aware instants under C3.
- Changing a user's timezone changes how times are displayed, not the
  underlying event time. Changing a facility's timezone does not rewrite
  historical timestamps.

Still open: the timezone-selection process, defaulting behavior, and
detailed display rules, including when a user timezone is appropriate
rather than the facility timezone named for schedule display in C3.

#### Item 8 — Database-Side Profile Provisioning

Issue: 6.2.4 provisions Profiles through a trusted database-side mechanism

Resolution — **RESOLVED** (2026-10-23):

- Profile provisioning must occur reliably when a new authenticated user
  is created.
- The provisioning flow must preserve domain-logic and authorization
  boundaries.
- Database triggers must not silently introduce business behavior that
  bypasses required validation or authorization.

Still open: whether provisioning uses an application/server-side workflow,

approval.
